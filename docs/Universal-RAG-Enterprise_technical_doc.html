01

Overview

The Universal RAG Agent automatically selects the optimal retrieval strategy for every query using a 5-dimension query analyzer. Rather than being locked into a single RAG approach, it routes each query through the best-fit pattern — or chains multiple patterns — based on query length, ambiguity, complexity, data type, and conversation state.

Key Features

Core Intelligence

14 RAG Patterns

All patterns implemented and auto-selected per query. No other system implements all 14 with intelligent routing.

Query Analysis

5-Dimension Query Analyzer

Routes each query to the right pattern(s) based on length, ambiguity, complexity, data type, and conversation state.

Ingestion

Multi-modal Ingestion

PDF, DOCX, TXT, Audio, Video, Web Pages, YouTube. Groq Whisper (whisper-large-v3) for audio/video transcription.

Memory

Self-Improving Memory

Tracks pattern performance, routing signals, and verified knowledge — gets measurably better with use.

LLM

3 LLM Providers

anthropic (production default), vertexai (GCP-native, no API key), groq (local dev/CI).

Observability

LangSmith Monitoring

Every LLM call traced with token counts, latency, cost, and quality scores. Full prompt replay for debugging.

API

Production FastAPI

JWT + OAuth2 + API Key auth, Redis-backed rate limiting, Prometheus metrics, structured audit log.

UI

Production Next.js 14

Replaces Streamlit — login, query, ingest, admin dashboard, role-based nav, mobile responsive.

Deployment

Two Deployment Targets

Cloud Run (serverless) or GKE Autopilot (K8s) — same images, one-command deploy via Cloud Build CI/CD.

LangSmith Monitoring

LangSmith traces every LLM call across all three providers automatically. No additional instrumentation needed in chain files — _configure_langsmith() sets the required env vars at startup and LangChain picks them up.

What Gets Traced

CallCaptured
synthesize()Full prompt, response, token count, latency
grade()Quality scores per dimension (relevance, completeness, hallucination risk)
check_faithfulness()Citation map, unsupported sentences flagged
generate_followups()Follow-up questions with confidence
Every retrieval chainChunks retrieved, reranker scores, pattern used

LangSmith Dashboard

  • Per-tenant traces — filter by enterprise, user, or session
  • Cost per query — token count × model rate, aggregated by day/week
  • Latency percentiles — p50 / p95 / p99 per RAG pattern
  • Quality score trends — track hallucination risk over time
  • Failure analysis — full prompt replay for any failed query

Auth Flow

Authentication Flow
User logs in → POST /api/auth/token
             ← access_token (stored in JS memory, not localStorage)
             ← refresh_token (stored in sessionStorage)

Every API call → Authorization: Bearer <access_token>
On 401        → auto-retry with refresh_token → POST /api/auth/refresh
On refresh fail → redirect to /login

Access token is never written to localStorage — mitigates XSS token theft.

Production Deployment

Option A — Cloud Run (Serverless, Recommended)

Fully managed — no cluster, no nodes, no infrastructure to maintain. Two scripts do everything.

Script 1 — Pre-flight check

cd universal-rag-agent-enterprise
export PROJECT_ID=your-gcp-project-id
bash scripts/preflight_check.sh

Checks gcloud, docker, git, python on PATH; correct repo directory; PROJECT_ID exported; GCP ADC file; API keys. Completes in under 5 seconds — no network calls.

⚠ One Manual Step

Before deploying, enable Vertex AI Claude in the GCP Console: console.cloud.google.com/vertex-ai/model-garden → search Claude → Enable. If you skip this, Cloud Run deploys fine but every LLM call returns 403 Permission Denied.

Script 2 — Full GCP deploy

bash scripts/deploy_gcp.sh

Provisions your entire production infrastructure in 9 sequential steps (~15 minutes total). Each step is idempotent — safe to re-run if anything fails midway.

Step 1

Enable GCP APIs (~1 min)

Turns on 10 GCP services: Cloud Run, Cloud SQL Admin, Redis (Memorystore), VPC Access, Vertex AI, Artifact Registry, Secret Manager, Cloud Build, Compute Engine, Service Networking.

Step 2

Artifact Registry (~30s)

Creates a private Docker image repository called rag-repo in your region. Also runs gcloud auth configure-docker so your local Docker can push to it.

Step 3

Cloud SQL PostgreSQL (~5 min)

Creates a PostgreSQL 16 instance with auto-growing storage, daily backups at 2am, point-in-time recovery. Creates ragdb database and raguser account. Saves password to Secret Manager.

Step 4

Serverless VPC Access Connector (~2 min)

Creates rag-vpc-connector that bridges Cloud Run to your VPC. Required because Memorystore Redis is VPC-internal only — Cloud Run containers cannot reach it without this.

Step 5

Memorystore Redis (~2 min)

Creates a managed Redis 7 instance named rag-redis (5GB, VPC-internal). Fetches private VPC IP and constructs the REDIS_URL the app uses for rate limiting and session caching.

Step 6

Pinecone Index (~30s)

Calls create_pinecone_index.py — creates the universal-rag index with dimension=384 and metric=cosine if it doesn't already exist, then polls until ready. Idempotent.

Step 7

Service Account + IAM Roles (~30s)

Creates GCP service account rag-cloudrun-sa and grants exactly 4 roles: aiplatform.user, cloudsql.client, secretmanager.secretAccessor, vpcaccess.user.

Step 8

Secret Manager (~30s)

Stores every credential as a named secret. Grants Cloud Build service account access so CI/CD can deploy without storing keys in the build config.

Step 9

Build Images → Push → Deploy Cloud Run (~5 min)

Builds Docker images for both services, tags each with git commit SHA + latest, pushes to Artifact Registry, deploys two Cloud Run services.

Cloud Run vs GKE — When to Use Which

Both options run the same Docker images from Artifact Registry. The choice is purely about the hosting model — not the application code.

Cloud RunGKE Autopilot
Node managementNoneNone (Autopilot manages nodes)
Cold startsYes — mitigated by --min-instances=1No — pods always running
Persistent WebSocketsNoYes
Custom sidecarsNoYes
Cost at low trafficLower — pay per request, scales to zeroHigher — min 2 pods (~$50–80/month minimum)
Setup complexity~15 min via deploy_gcp.sh~25 min via setup_gke.sh + GKE cluster
Best forMost enterprise deploymentsSpecific K8s requirements only

Cost at Low Traffic (10,000 req/month)

Cloud RunGKE Autopilot
Compute~$5–15~$80–120
Pay modelPer requestPer pod-hour
Scales to zeroYes (but min-instances=1 keeps 1 warm)No

Decision Guide

Choose Cloud Run if

Starting a new enterprise deployment · team doesn't use Kubernetes · zero infrastructure maintenance · traffic is bursty or unpredictable · no WebSockets or sidecars needed

Choose GKE Autopilot if

Organization already has GKE cluster and K8s expertise · need persistent WebSocket connections · need sidecar containers (service mesh, log agents) · sustained high traffic where pod-hour pricing is cheaper

✦ Default

This project defaults to Cloud Run. GKE support is fully wired via scripts/setup_gke.sh and infra/k8s/deployment.yml for teams that need it.

Local Pipeline — build_and_test.sh

Runs 7 stages in order. Each stage must pass before the next one starts. If any stage fails the script exits immediately.

Stage 1
Lint (ruff)Checks code style, import ordering, unused variables across src/, api/, tests/. Fast — runs in under 3 seconds.
Stage 2
Type check (mypy)Static type analysis. Catches type mismatches before they become runtime errors — especially important for the LLM provider switching code.
Stage 3
Security scan (bandit)SAST tool. Scans for hardcoded passwords, insecure functions (eval, pickle), SQL injection risks, weak random number generation. Only HIGH and MEDIUM severity issues fail the build.
Stage 4
Tests + coverage gate (pytest) ← THE GATERuns all 81 tests and enforces 70% coverage. All external services mocked — Pinecone, Redis, LLM. Zero network calls, no API keys needed. If this fails → Stages 5, 6, and 7 never run. No images are produced.
Stage 5
Build API image (Docker)docker build -f Dockerfile -t rag-api:TAG . — tagged with commit SHA + latest. Only runs because Stage 4 passed.
Stage 6
Build Frontend image (Docker)docker build -f Dockerfile.nextjs — multi-stage build. Final image is ~150MB, contains only compiled output, not source code or node_modules.
Stage 7
Smoke testStarts the API container locally, waits up to 40 seconds, hits /api/health (must return {"status": "ok"}), then stops the container. Catches startup failures that pass unit tests.

4 LLM Roles & 4 Memory Layers

4 LLM Roles

Synthesizer

Generates the final answer from retrieved chunks. Instructed to never use prior knowledge — only what the chunks provide.

Grader

Scores answer quality 0.0–1.0 across three dimensions: relevance, completeness, and hallucination risk.

Verifier

Checks faithfulness — every sentence in the answer must be supported by a specific source chunk. Flags unsupported sentences.

Judge

Resolves conflicting information across sources — determines which source to trust and why.

4 Memory Layers

Conversation History

Tracks dialogue context per session — enables follow-up questions without re-stating context.

Pattern Performance

Learns which patterns work best per query type — routing improves over time as more queries are processed.

Routing Signals

Improves future routing decisions — 5-dimension analysis gets more accurate with accumulated data.

Verified Knowledge Cache

Stores high-confidence answers (score ≥ 0.85) for instant reuse — identical queries return in <50ms at $0 cost.

Pinecone Index Setup

Auto-created — no manual step required. Before the app can store or search any documents, Pinecone needs a pre-configured index — think of it like creating a database table before you can insert rows. You cannot insert vectors into an index that does not exist.

What an Index Is

Pinecone stores document embeddings as vectors. An index defines two things that can never be changed after creation:

SettingValueWhy It Matters
dimension=384Must match all-MiniLM-L6-v2 outputIf the index dimension doesn't match the embedding model, every insert fails
metric=cosineSimilarity measure for searchDetermines how "closeness" between vectors is calculated
⚠ Critical

If either setting is wrong, you have to delete the index and recreate it — losing all indexed documents.

Why It Needs to Exist Before the App Starts

Ingest Flow — Index Must Exist
User uploads a document
        │
        ▼
FastAPI calls ingest()
        │
        ▼
SentenceTransformer generates 384-dim embeddings
        │
        ▼
Pinecone.Index("universal-rag").upsert(vectors)
        │
        ├── Index EXISTS → vectors stored ✓
        │
        └── Index DOES NOT EXIST → exception, ingest fails ✗

Three Ways It Gets Created (all automatic)

The system never requires you to manually create the index in the Pinecone dashboard.

Index Creation — Three Paths
Option 1 — setup.sh (local first-time setup)
  bash setup.sh
  └── calls create_pinecone_index.py automatically

Option 2 — Standalone script (if you skipped setup.sh)
  python scripts/create_pinecone_index.py
  └── creates index if missing, skips if already exists (idempotent)

Option 3 — _ensure_index() inside vector_store.py (last resort)
  └── called automatically inside _get_index()
      before every retrieve() or ingest() call
      if the index somehow doesn't exist, it creates it on the spot

What create_pinecone_index.py Actually Does

create_pinecone_index.py — Execution Flow
Start
  │
  ▼

  ▼

  │
